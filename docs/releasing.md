# 发布维护

发布附件包含八份独立 PDF 和 `namishu-printables-pdf.zip`。汉字卡使用内置 300 字完整版本，文档样例仍只展示“天地”。

## 本地构建

安装项目及开发依赖后执行：

```bash
uv run python scripts/build_pdf_bundle.py
```

文件输出到 `dist/pdf/`。工具会检查 PDF 页数和页面内容，并校验 ZIP；输出目录已存在时会报错，避免覆盖待检查的附件。也可以用 `--output` 指定新的目录。

CI 会在 Windows、macOS 和 Linux 上，从独立环境安装构建出的 wheel，再生成并检查整套 PDF。

## 更新记录

用户能感知的新功能、布局变化、默认内容变化和问题修复记录在 [CHANGELOG.md](../CHANGELOG.md) 的“未发布”部分。格式整理等内部改动无需逐项记录。

准备版本时，将该部分整理为 `## 0.1.0 - YYYY-MM-DD` 这样的标题，并同步包版本。发布工作流会核对标签、包版本和更新记录，提取该版本内容作为 Release 说明。

## 发布步骤

1. 检查全部 CI 通过，查看生成的 PDF，整理版本号和更新记录。
2. 向项目负责人展示版本、变化和附件，得到确认后才创建并推送版本标签，例如 `v0.1.0`。
3. 标签触发完整检查；通过后自动生成附件并创建草稿 Release。
4. 检查草稿附件，确认获准正式发布后，再手动发布草稿。

工作流不会自动公开发布草稿。仓库为私有时，Release 附件仅对有仓库访问权限的人开放。

## 下载链接

首次正式发布后，在首页增加整套下载入口，并在各模块文档加入对应正式 PDF 的链接。发布前继续使用现有样例链接，避免提供尚不存在的下载地址。

整套下载地址使用 `https://github.com/namishu/printables/releases/latest/download/namishu-printables-pdf.zip`；单份 PDF 使用同一路径下的对应文件名。
